# «Решено» — ТЗ на backend MVP

Версия 2.0 · 18.10.2026 · заменяет `backend_requirements.md` v1.1 (оставлен как справочник).

Документ написан для будущих сессий разработки: из него должно быть понятно, **что строим, зачем, что входит и что нет, и какие решения уже приняты**. Решения команды помечены **[РЕШЕНО]**, мои допущения, которые пользователь явно не подтверждал, помечены **[ДОПУЩЕНИЕ]**. Допущения можно менять без согласования, но изменение нужно записать в раздел 12.

---

## 1. Идея

**«Решено»** — AI-помощник по проекту. Он отвечает на вопросы о проекте, опираясь на то, что реально лежит в репозитории, и тем самым сокращает число вопросов «коллеге в личку».

Типичные вопросы: «Где описан процесс релиза?», «Как настроен деплой?», «Кто и когда менял логику расчёта?», «Какой формат у этого API?». Ответы почти всегда уже есть в README, документации, коде, issues и истории коммитов. Каждый такой вопрос коллеге отнимает время у двоих.

### Как работает (сквозной сценарий)

1. Пользователь **регистрируется** в сервисе.
2. **Подключает репозиторий GitHub** (один). Сервис строит индекс проекта.
3. Пользователь задаёт вопрос двумя способами:
   - в **чате веб-приложения**;
   - из **почты**: пишет письмо-вопрос коллеге и перед отправкой нажимает кнопку **«Спросить у ИИ»** (кнопка — часть браузерного расширения над веб-почтой).
4. Перед каждым ответом система **ищет по всему проекту** (по актуальному индексу) и отвечает, указывая источники.
5. Если ответ подошёл, пользователь не отправляет письмо. Если нет, отправляет как обычно.
6. После каждого коммита в репозиторий индекс **обновляется автоматически**, поэтому ответы опираются на свежее состояние проекта.

### Ключевые принципы

- **[РЕШЕНО]** ИИ ничего не отправляет и не создаёт сам; итоговое действие всегда за пользователем.
- **[РЕШЕНО]** Если подтверждения в проекте нет, ИИ так и говорит и не выдумывает файлы, факты, цитаты.
- **[РЕШЕНО]** Ответ всегда с источниками (файл, фрагмент, коммит).
- **[РЕШЕНО]** Backend **не ходит в почту**: расширение само передаёт текст черновика и цепочку переписки в запросе. Пароли ящиков и почтовые протоколы не нужны.
- **[ДОПУЩЕНИЕ]** Пользователь видит знания только того репозитория, к которому у него есть доступ (его токен).

## 2. Что входит и что нет

### Входит в MVP
- Регистрация и вход.
- Подключение **одного GitHub-репозитория** (публичного или приватного через токен пользователя).
- Индексация репозитория: файлы, документация, при возможности issues и PR; **граф проекта через graphify**; автоматическое обновление индекса после коммитов (вебхук GitHub).
- Чат-вопросы по проекту (с историей диалога).
- Эндпоинт «Спросить у ИИ» для браузерного расширения: принимает текст черновика и цепочку переписки.
- Логирование вопросов и оценки ответа «помогло / не помогло».
- OpenAPI-контракт для фронтенда и расширения.

### Не входит в MVP
- Организации GitHub, GitLab, несколько репозиториев на пользователя.
- Команды, приглашения, роли, блокировка для одиночки (обсуждались раньше, **из MVP выпали**; см. раздел 11).
- Заявки со сроками, SLA, дашборд эффекта и расчёт «предотвращённых обращений».
- Почтовые коннекторы (IMAP, SMTP, Gmail API), облачный диск и общие документы вне репозитория.
- Автоматическая отправка писем, поиск по локальному ПК, редактирование исходных документов.
- Сам фронтенд и расширение браузера — их делает другая часть команды. Backend отдаёт API и OpenAPI.

## 3. Пользователи и роли

Одна роль — **пользователь**. Он владеет подключённым репозиторием и видит только свои данные.

## 4. Технологии

**[РЕШЕНО]**
- Python 3.12, FastAPI, PostgreSQL с расширением pgvector.
- Docker Compose: `api`, `postgres`, `worker`.
- LLM: **основной GigaChat, запасной YandexGPT**. Оба за общим интерфейсом, при сбое основного автоматически включается запасной. Ключи у пользователя уже есть.
- Эмбеддинги получаем у одного провайдера на проект (не смешиваем в одном индексе).
- Только GitHub, приватные репозитории — через токен пользователя (PAT или OAuth).
- Граф проекта — инструмент **graphify** (pip-пакет `graphifyy`, результат `graph.json`, поддерживает инкрементальное обновление `--update`).

**[ДОПУЩЕНИЕ]**
- Фоновые задачи (индексация, обновление) — очередь на PostgreSQL или лёгкая очередь внутри worker; отдельный брокер не вводим, пока не понадобится.
- Вход по email и паролю, выдача JWT; для расширения — отдельный долгоживущий API-токен, который можно отозвать.

## 5. Архитектура (логические модули)

Для MVP допустим один монолит с чётко разделёнными модулями:

| Модуль | Назначение |
|---|---|
| `auth` | Регистрация, вход, JWT, API-токены для расширения |
| `repos` | Подключение репозитория, хранение токена (в шифрованном виде), статус индексации |
| `github` | Клиент GitHub: чтение файлов, issues/PR, коммитов; приём вебхуков и проверка подписи |
| `indexer` | Разбор репозитория на фрагменты, эмбеддинги, запись в pgvector; запуск graphify |
| `retrieval` | Поиск по индексу и графу, ранжирование, сбор контекста для модели |
| `llm` | Адаптеры GigaChat и YandexGPT, fallback, таймауты, повторы |
| `qa` | Оркестрация ответа: разбор вопроса, поиск, генерация, привязка источников, проверка «подтверждено или нет» |
| `mail_assist` | Эндпоинт «Спросить у ИИ»: разбор черновика и переписки, выделение вопроса |
| `feedback` | Логи вопросов и оценка «помогло / не помогло» |
| `worker` | Фоновая индексация и обновление по вебхуку |

## 6. Функциональные требования

### 6.1 Аккаунты
- **FR-AUTH-01.** Регистрация по email и паролю, вход, обновление токена.
- **FR-AUTH-02.** Создание и отзыв API-токена для расширения.
- **FR-AUTH-03.** Данные пользователей изолированы: пользователь не получает чужие репозитории, индексы, вопросы.

### 6.2 Подключение репозитория
- **FR-REPO-01.** Пользователь передаёт ссылку на репозиторий GitHub и токен (для приватных). Сервис проверяет доступ и отвечает явной ошибкой, если доступа нет.
- **FR-REPO-02.** У пользователя ровно один подключённый репозиторий в MVP; повторное подключение заменяет прежний (с подтверждением).
- **FR-REPO-03.** Статус индексации отдаётся значениями: `not_connected`, `indexing`, `ready`, `updating`, `error`, `reauth_required`. При `reauth_required` старый индекс остаётся доступным.
- **FR-REPO-04.** Токен хранится только в зашифрованном виде и не попадает в логи.
- **FR-REPO-05.** При подключении сервис сам регистрирует вебхук GitHub на событие `push` (или принимает инструкцию, как его настроить вручную, если у токена нет прав).

### 6.3 Индексация и граф
- **FR-IDX-01.** Первичная индексация: файлы (исходный код, документация, конфигурация), README, wiki при наличии, issues и PR (если токен позволяет). Бинарные и слишком большие файлы пропускаются с отметкой в статусе.
- **FR-IDX-02.** Фрагменты хранят метаданные: путь, коммит, дата, автор, тип (код, документ, issue).
- **FR-IDX-03.** Граф проекта строится graphify и сохраняется вместе с версией индекса (`graph.json` и краткий отчёт).
- **FR-IDX-04.** После каждого `push` обновляется только то, что изменилось (инкрементально). Обработка идемпотентна: повторный вебхук не ломает индекс.
- **FR-IDX-05.** Пока идёт обновление, ответы строятся по предыдущей версии индекса; в ответе указывается коммит, по которому он построен.
- **FR-IDX-06.** Секреты (ключи, пароли, `.env`) в индекс не попадают; перед индексацией выполняется простая проверка и исключение таких файлов.

### 6.4 Вопросы и ответы
- **FR-QA-01.** Эндпоинт вопроса: текст вопроса и (необязательно) идентификатор диалога. Ответ: текст, список источников, статус `answered | partial | not_found`, коммит, по которому построен индекс.
- **FR-QA-02.** Поиск идёт по индексу и графу (векторный поиск плюс обход связей графа); контекст для модели собирается только из найденного.
- **FR-QA-03.** Каждое утверждение с фактами (имя, число, путь, срок) связывается с источником. Если источника нет, утверждение не показывается или помечается как неподтверждённое.
- **FR-QA-04.** Если ничего не найдено, ответ — `not_found` с понятным сообщением и без выдумок.
- **FR-QA-05.** Диалог: следующий вопрос учитывает предыдущие в рамках сессии; можно начать новую.
- **FR-QA-06.** Открытие источника: эндпоинт возвращает фрагмент и ссылку на файл в GitHub.
- **FR-QA-07.** Защита от prompt injection: содержимое репозитория и переписки передаётся модели как **данные**, а не инструкции; команды внутри файлов или писем не меняют поведение системы.

### 6.5 «Спросить у ИИ» (почта)
- **FR-MAIL-01.** Эндпоинт принимает: текст черновика, тему, получателей (для контекста, не для отправки) и цепочку текущей переписки.
- **FR-MAIL-02.** Система выделяет из черновика вопросы и ищет ответ по проекту так же, как в чате; переписка используется как контекст (о чём спор, что уже обсуждали).
- **FR-MAIL-03.** Ответ содержит: найденный ответ с источниками, статус по каждому вопросу и рекомендацию «ответ найден, письмо можно не отправлять» или «ответа нет, отправьте письмо».
- **FR-MAIL-04.** Система **не блокирует** отправку и ничего не отправляет сама.
- **FR-MAIL-05.** Содержимое переписки не сохраняется после обработки. В журнал пишутся только служебные данные (время, статус, хэш вопроса) — **[ДОПУЩЕНИЕ]**, уточнить при реализации приватности.

### 6.6 Обратная связь
- **FR-FB-01.** Для каждого ответа можно поставить оценку «помогло» или «не помогло» и необязательный комментарий.
- **FR-FB-02.** Хранится история вопросов (с учётом FR-MAIL-05), оценки и статус ответа. Расчёт метрик в MVP не делается, но данные собираются, чтобы позже посчитать долю помогших ответов.

### 6.7 Надёжность
- **FR-REL-01.** Единый формат ошибок: `{ "code": "...", "message": "...", "retryable": true|false }`, сообщения на русском.
- **FR-REL-02.** Таймауты и сбои LLM: переключение на запасного провайдера; если оба недоступны — понятная ошибка, а не пустой ответ.
- **FR-REL-03.** Ответ можно получать потоком (SSE), чтобы интерфейс показывал статус «Ищем в проекте…».

## 8. API (черновой контракт)

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/auth/register`, `/auth/login`, `/auth/refresh` | Аккаунт |
| POST/DELETE | `/auth/api-tokens` | Токены для расширения |
| GET | `/me` | Профиль и статус репозитория |
| POST | `/repo/connect` | Подключить репозиторий |
| GET | `/repo/status` | Статус индекса |
| DELETE | `/repo` | Отключить репозиторий |
| POST | `/github/webhook` | Приём `push` (проверка подписи) |
| POST | `/qa/ask` | Вопрос в чат (поддержка SSE) |
| GET | `/qa/conversations/{id}` | История диалога |
| GET | `/sources/{id}` | Открыть источник |
| POST | `/mail/ask` | «Спросить у ИИ» из письма |
| POST | `/feedback` | Оценка ответа |

OpenAPI-схема генерируется FastAPI и отдаётся фронту и команде расширения.

## 9. Нефункциональные требования

- **NFR-01.** Время ответа: первый фрагмент потока до 5 с, полный ответ до 20 с (ориентир).
- **NFR-02.** Пользовательские данные изолированы по `user_id`.
- **NFR-03.** Токены репозиториев и ключи LLM — только в зашифрованном виде или в переменных окружения, в репозиторий не коммитятся.
- **NFR-04.** Логи без текстов вопросов, переписки и содержимого репозитория.
- **NFR-05.** Выбор LLM-провайдера и режим fallback — в конфигурации.
- **NFR-06.** Один `docker compose up` поднимает всё необходимое для локального запуска.

### Конфигурация по умолчанию (всё меняется в конфиге)
Язык интерфейса и ответов — русский; пауза ввода для расширения — 3 с; таймауты LLM — 30 с на запрос.

## 10. Критерии приёмки

| Проверка | Ожидаемый результат |
|---|---|
| Подключение | Репозиторий подключается, статус доходит до `ready`; без доступа возвращается явная ошибка |
| Вопрос в чате | Вопрос по содержимому репозитория даёт ответ с источниками; вопрос вне проекта даёт `not_found`, без выдумок |
| Обновление | После нового коммита ответ учитывает изменение; ответ указывает коммит |
| «Спросить у ИИ» | Черновик с вопросом и цепочка переписки дают ответ и рекомендацию; письмо не отправляется |
| Приватность | Чужие репозитории и чужой индекс недоступны; в логах нет содержимого |
| Инъекции | Команда внутри файла или письма не меняет поведение системы |
| Fallback | При недоступности основного LLM ответ приходит от запасного |
| Обратная связь | Оценка «помогло / не помогло» сохраняется |

## 11. Контекст и история решений

Изначально проект описывался как ИС для корпоративной почты с перехватом исходящих вопросов, заявками, командами с ролями и дашбордом эффекта (`backend_requirements.md` v1.1). 18.10.2026 команда **упростила идею** до Q&A по репозиторию с кнопкой «Спросить у ИИ» в почте.

Идеи, обсуждавшиеся и **отложенные**:
- Команды с главой и приглашением по ссылке, блокировка продукта для одиночки (логика: в одиночку писать некому, ценность только в команде).
- Роли (`admin`, специалист ИБ, руководитель), политики безопасности.
- Заявки с ответственным и сроком; метрика «процент предотвращённых обращений» и сэкономленные часы.
- Организации GitHub и GitLab.
- Облачный диск и общие документы как отдельный источник.

Если вернёмся к этим идеям, архитектура должна позволять добавить их поверх: тип источника `repo` уже выделен, пользователь изолирован по `user_id`, а `QuestionLog` и `Feedback` собирают данные для будущей метрики.

## 12. Открытые вопросы и допущения

Нужно подтвердить или изменить при реализации:

1. **Аутентификация пользователей:** email и пароль плюс JWT — допущение; возможно, понадобится вход через GitHub OAuth (он же даёт токен репозитория).
2. **Токен GitHub:** пока считаем, что пользователь вставляет PAT; OAuth-приложение GitHub — опция на потом.
3. **graphify и LLM:** не проверено, нужен ли ему внешний LLM для разбора документов (для кода, судя по описанию, не нужен). До опоры на него проверить на тестовом репозитории; если нужен LLM, подключить GigaChat.
4. **Размер репозитория:** лимит на размер и число файлов для MVP не задан; предложение — установить лимит в конфиге и отказывать с понятной ошибкой.
5. **Хранение переписки из «Спросить у ИИ»:** допущено, что тексты не сохраняются (FR-MAIL-05).
6. **Эмбеддинги:** какой именно провайдер (GigaChat или YandexGPT) используется — выбрать при реализации по доступности и качеству на русском.
7. **Отзыв доступа:** если токен репозитория отозван, статус `reauth_required` и старый индекс остаётся доступным — допущение.

## 13. Что нужно от команды перед стартом

- Ключи GigaChat (Authorization key и scope) и YandexGPT (API-ключ и folder id).
- Тестовый репозиторий GitHub и токен доступа к нему.
- Договорённость с командой фронта и расширения по формату `POST /mail/ask` и по способу передачи цепочки переписки.
