# Архитектура

```
                    интеграторы: почта (демо), мессенджеры, порталы…
                                   │  X-Api-Key, /v1
 владелец / админ / ТП ──браузер──►│
                                   ▼
        ┌──────────────── admin-web (nginx) ────────────────┐   публичный вход
        │  /            сайт администратора (React)         │
        │  /panel/api   API сайта (cookie-сессия)           │
        │  /v1          открытый API для интеграций         │
        │  /jira        вебхук Jira (подпись)               │
        └───────────────────────┬───────────────────────────┘
                                ▼
        ┌──────────────── admin (FastAPI) ──────────────────┐   ядро платформы
        │ проекты, коды, статусы, входы на сайт             │
        │ ask-прокси (разделы участника → RAG)              │
        │ вопросы без ответа → админам                      │
        │ обращения в ТП ↔ Jira                             │
        │ outbox событий: опрос /v1/events + вебхуки        │
        │ Postgres (admin-db), Redis (лимиты)               │
        └───────────────────────┬───────────────────────────┘
                     служебный токен, внутренняя сеть
                                ▼
        ┌──────────────── llm (FastAPI) ────────────────────┐   скрыт
        │ RAG: агент с инструментами, гибридный поиск        │
        │ (dense + BM25 → RRF → реранкер), проверка цитат,  │
        │ кэши ответов, аналитика, индексация документов    │
        │ Qdrant, Redis, Postgres (llm-db)                  │
        └───────────────────────────────────────────────────┘

        ┌──────────────── mail (демо-интеграция) ───────────┐
        │ mail-web (React) + mail-api (FastAPI) + mail-db   │
        │ свои пользователи; IMAP/SMTP; «Спросить у ИИ»;    │
        │ в платформу — только через /v1, как любой клиент  │
        └───────────────────────────────────────────────────┘
```

Как в Innopolis: пользователь не видит RAG-сервис. Там с ним работали `tg_bot` и `mini_app`, здесь — `admin`,
а снаружи на платформу смотрят интеграции (`mail` — одна из них) и сайт администратора.

## Сервисы

| Сервис | Код | Хранит | Наружу |
|---|---|---|---|
| `llm` | `services/llm` (`rag_service`, перенос `bars_rag` из Innopolis) | Qdrant (фрагменты, векторы), Redis (сессии диалога, точный кэш), Postgres (ходы, оценки, задачи), `var/` (загрузки, состояние проектов) | нет |
| `admin` | `services/admin/backend` (`admin_api`), `services/admin/frontend` | Postgres: интеграции, проекты, участники, входы, ходы, вопросы, обращения, Jira, события | `admin-web` |
| `mail` | `services/mail/backend` (`mail_api`), `services/mail/frontend` | Postgres: пользователи почты, ящики (пароли зашифрованы), текущий проект, уведомления | `mail-web` |

## Ключевые решения

**Идентичность принадлежит интегратору.** Платформа не регистрирует конечных пользователей: интеграция
передаёт свой `external_id` и статус. Отсюда же граница доверия: ключ интеграции = доверие к её id.
Правила статусов (кто кого может назначить) проверяет платформа.

**Вход на сайт = логин + пароль + код проекта.** Код выдаётся создателю один раз (в базе — argon2-хеш для
проверки и Fernet-шифротекст, чтобы владелец мог его посмотреть). Пароли задаются по одноразовой ссылке,
через API не передаются. Сессия — httpOnly-cookie; изменяющие запросы обязаны нести `X-Requested-With: panel`
(CSRF). Неверный код, логин или пароль дают одинаковую ошибку; попытки ограничены по IP и логину.

**Разделы документации.** Файлы проекта лежат в RAG как `<проект>/<раздел>/<файл>`. Admin передаёт с каждым
вопросом `allowed_sections` участника; RAG превращает их в набор скрытых документов на время хода
(контекстная переменная), и его учитывают все места, которые уже знали про скрытые документы: поиск,
инструменты агента, кэши, ссылки на документы. «Заменить раздел» заменяет только раздел и требует код проекта.

**Изоляция проектов в RAG.** `project_id` всегда подставляет admin (`p-<public_id>`); клиент его не передаёт.
Каждый поиск в Qdrant фильтруется по проекту и активной версии базы; загрузки и ответы поддержки,
сохранённые в базу, лежат в папке своего проекта.

**События — outbox.** Изменение и событие о нём пишутся в одной транзакции. Читать можно опросом по курсору
(`id` события) или получать вебхуком с подписью HMAC и повторами; доставка «как минимум один раз».
Демо-почта читает опросом — ей не нужен публичный адрес.

**Jira — зеркало, а не источник истины.** Обращение создаётся в базе платформы сразу; задача в Jira создаётся
воркером идемпотентно (метка `idem-…` по номеру обращения, сверка перед повтором). Комментарии и смены статуса
уходят очередью; вебхук Jira (подпись `X-Hub-Signature`) приносит ответы специалистов и закрытие. Если Jira
недоступна, обращение работает с сайта, а синхронизация догонит.

**Вопросы без ответа — админам, просьба о человеке — в ТП.** `offer_operator` (в документации нет ответа)
и 👎 создают вопрос для владельца и админов; их ответ доходит до пользователя событием и может сохраниться в
базу знаний, после чего бот отвечает сам. `escalate` (пользователь попросил человека) открывает обращение в ТП.
Технические сбои (модель недоступна, лимит времени) пробелом в документации не считаются.

## Масштаб и ограничения

- `admin` и `mail` stateless, масштабируются копиями; лимиты API и входа — в Redis.
- Воркеры (вебхуки, Jira, слежение за индексацией) работают в процессе `admin` и берут строки с
  `FOR UPDATE SKIP LOCKED` — несколько копий не отправят одно событие дважды. Сетевой вызов идёт внутри
  транзакции с блокировкой строки: до сотен событий в минуту этого достаточно, дальше — аренда с таймаутом.
- `llm` — один процесс: состояние проектов (активная версия базы) и кэш FAQ лежат в файлах `var/`
  (запись атомарная). Для нескольких копий их нужно перенести в Postgres.
- Статистика считается по строкам периода в Python — рассчитано на тысячи вопросов в месяц на проект;
  дальше нужна агрегация в SQL или дневные срезы.
