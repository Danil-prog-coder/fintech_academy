# «Решено» — техническая документация backend

Версия 1.0 · 18.10.2026

Документ описывает, как устроен backend MVP. Что и зачем строим, написано в [../docs/TZ_MVP.md](../docs/TZ_MVP.md); здесь только техническая сторона.

Пометки: **[РЕШЕНО]** — решение команды, **[ДОПУЩЕНИЕ]** — моё предложение, которое можно менять (изменения записывайте в раздел 11). Раздел 3 (структура) и часть библиотек остаются проектом; фактическое состояние кода описано в разделе 12.

---

## 1. Что делает backend

Пользователь регистрируется, подключает один репозиторий GitHub и задаёт вопросы по проекту: в чате веб-приложения или кнопкой «Спросить у ИИ» в почте (через браузерное расширение). Backend:

1. индексирует репозиторий и обновляет индекс после каждого коммита;
2. на каждый вопрос ищет по индексу, собирает контекст и просит нейросеть ответить;
3. возвращает ответ с источниками (файл, фрагмент, коммит) или честное `not_found`;
4. сохраняет вопросы и оценку «помогло / не помогло».

В MVP **нет**: заявок, дашборда, команд и приглашений, организаций GitHub, почтовых коннекторов, графа graphify (не используется).

## 2. Стек и правила

**[РЕШЕНО]**
- Python 3.12, FastAPI.
- **Весь код асинхронный** (`async def`, `await`).
- PostgreSQL + pgvector.
- LLM: GigaChat (основной), YandexGPT (запасной). Ключи лежат в `.env`.
- Docker Compose: `api`, `worker`, `postgres`.

**[ДОПУЩЕНИЕ] библиотеки**

| Назначение | Библиотека |
|---|---|
| Сервер | `uvicorn` |
| Конфиг | `pydantic-settings` (читает `.env`) |
| БД | `SQLAlchemy 2.x` (async) + `asyncpg` |
| Миграции | `alembic` |
| Векторы | `pgvector` (Python-пакет для SQLAlchemy) |
| HTTP-клиент | `httpx.AsyncClient` |
| Валидация | `pydantic v2` |
| Пароли и токены | `passlib[argon2]` (или `argon2-cffi`), `pyjwt` |
| Шифрование токенов GitHub | `cryptography` (Fernet) |
| Тесты | `pytest`, `pytest-asyncio`, `respx` (моки HTTP) |
| Линтер и формат | `ruff` |

### Правила асинхронности

1. В `async def` запрещены блокирующие вызовы: `requests`, `time.sleep`, синхронный драйвер БД, чтение больших файлов обычным `open`. Вместо них — `httpx.AsyncClient`, `asyncio.sleep`, `asyncpg`, `aiofiles` или `asyncio.to_thread`.
2. Тяжёлая CPU-работа (разбор файлов на фрагменты, подсчёт токенов) выносится в `asyncio.to_thread` или в процесс worker, а не выполняется в обработчике запроса.
3. Один `httpx.AsyncClient` на провайдера создаётся при старте приложения (в `lifespan`) и закрывается при остановке; на каждый запрос новый клиент не создаётся.
4. Любой внешний вызов имеет таймаут. Запросы к LLM и GitHub не должны висеть бесконечно.
5. Параллельные независимые вызовы (например, эмбеддинг вопроса и загрузка истории диалога) запускаются через `asyncio.gather` / `asyncio.TaskGroup`.
6. Сессия БД создаётся на запрос через зависимость FastAPI и не передаётся между задачами.

## 3. Архитектура

### Компоненты

| Процесс | Что делает |
|---|---|
| `api` | HTTP-запросы: аккаунты, подключение репозитория, вопросы, обратная связь, приём вебхука GitHub |
| `worker` | Фоновые задачи: первичная индексация, обновление после коммита |
| `postgres` | Данные, очередь задач и векторный индекс |

### Поток вопроса

1. Клиент (веб-приложение или расширение) шлёт `POST /qa/ask` или `POST /mail/ask`.
2. `api` проверяет пользователя и статус репозитория.
3. Вопрос превращается в эмбеддинг (через LLM-слой).
4. Поиск по pgvector в индексе этого репозитория, отбор лучших фрагментов.
5. Из фрагментов и вопроса собирается запрос к нейросети; содержимое репозитория и переписки передаётся как **данные**, не как инструкции.
6. Ответ проверяется: каждый факт связан с источником, иначе помечается неподтверждённым или не показывается.
7. Клиент получает ответ целиком или потоком (SSE).

### Поток индексации

1. Пользователь подключает репозиторий (`POST /repo/connect`), `api` проверяет токен и создаёт задачу в таблице `jobs`.
2. `worker` берёт задачу, скачивает содержимое репозитория через GitHub API, режет файлы на фрагменты, считает эмбеддинги, записывает в `chunks`.
3. GitHub присылает вебхук `push` на `POST /github/webhook`. `api` проверяет подпись и ставит задачу на обновление.
4. `worker` определяет изменённые файлы (сравнение коммитов), пересчитывает только их.
5. Пока идёт обновление, ответы используют прошлую версию индекса; после успеха версия переключается атомарно.

## 4. Конфигурация и `.env`

Все настройки читаются из переменных окружения через `pydantic-settings`; локально они берутся из файла `.env`.

### Правила для секретов

- `.env` **не коммитится**: он должен быть в `.gitignore`.
- В репозитории лежит только `.env.example` с именами переменных и пустыми или безопасными значениями.
- Ключи не пишутся в логи, в ответы API и в тексты ошибок.
- Токены GitHub пользователей хранятся в БД только зашифрованными (ключ шифрования — в `.env`).

### Переменные **[ДОПУЩЕНИЕ: имена можно менять]**

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | Строка подключения к PostgreSQL, драйвер `postgresql+asyncpg://…` |
| `SECRET_KEY` | Ключ подписи JWT |
| `ENCRYPTION_KEY` | Ключ (Fernet) для шифрования токенов GitHub |
| `ACCESS_TOKEN_TTL_MIN` | Срок жизни access-токена |
| `GIGACHAT_CREDENTIALS` | Authorization key GigaChat |
| `GIGACHAT_SCOPE` | Область доступа (например, для физических лиц) |
| `GIGACHAT_MODEL` | Модель генерации |
| `GIGACHAT_EMBEDDINGS_MODEL` | Модель эмбеддингов |
| `GIGACHAT_CA_BUNDLE` | Дополнительный сертификат УЦ. Сертификат российского УЦ встроен в код (`app/llm/russian_ca.py`), переменная не обязательна |
| `YANDEX_API_KEY` | API-ключ YandexGPT |
| `YANDEX_FOLDER_ID` | Идентификатор каталога Yandex Cloud |
| `YANDEX_MODEL` | Модель генерации |
| `LLM_PRIMARY` | Основной провайдер (`gigachat` или `yandex`) |
| `LLM_FALLBACK` | Запасной провайдер |
| `EMBEDDINGS_PROVIDER` | Провайдер эмбеддингов (`gigachat` по умолчанию, `local` позже) |
| `LLM_TIMEOUT_SEC` | Таймаут запроса к модели (по умолчанию 30) |
| `GITHUB_WEBHOOK_SECRET` | Секрет для проверки подписи вебхука |
| `PUBLIC_BASE_URL` | Внешний адрес API (нужен для регистрации вебхука) |
| `MAX_REPO_FILES`, `MAX_FILE_BYTES` | Ограничения индексации |
| `LOG_LEVEL` | Уровень логирования |

Классы `Settings` создаются один раз при старте; приложение должно **падать при запуске**, если обязательная переменная отсутствует, а не в момент первого запроса.

## 5. LLM-слой

Один интерфейс, два провайдера, автоматический запасной.

### Интерфейс **[ДОПУЩЕНИЕ]**

```python
class LLMProvider(Protocol):
    name: str
    async def complete(self, messages: list[Message], *, temperature=None, max_tokens=None) -> LLMResult: ...
    def stream(self, messages: list[Message], *, temperature=None, max_tokens=None) -> AsyncIterator[str]: ...


class EmbeddingProvider(Protocol):
    name: str
    dim: int
    async def embed(self, texts: list[str]) -> list[list[float]]: ...
```

Ошибки (`app/llm/base.py`): `LLMNotConfiguredError` (503, нет ключей), `LLMAuthError` (неверные ключи, fallback не включается), `LLMUnavailableError` (таймаут, 429, 5xx; `retryable`, допустим fallback), `LLMResponseError` (неожиданный ответ).

Реализовано: `app/llm/gigachat.py` (авторизация с кэшем токена под `asyncio.Lock`, чат, потоковый чат, эмбеддинги пакетами с `Semaphore`, повторы на 429/5xx, одно обновление токена на 401). `app/llm/yandex.py` (YandexGPT) и `app/llm/router.py` (fallback) написаны. Проверка на живых ключах: `python -m scripts.check_gigachat`.

Остальной код работает только с этими интерфейсами и не знает, какой провайдер ответил. Провайдер эмбеддингов выбирается переменной `EMBEDDINGS_PROVIDER` (`gigachat` по умолчанию, `local` — локальная модель на VPS, позже).

### Fallback

- `router.py` вызывает основного провайдера; при таймауте, ошибке сети или 5xx — один раз запасного.
- При ошибке авторизации (неверный ключ) запасной не включается молча: ошибка пишется в лог, пользователю возвращается код ошибки провайдера.
- В ответе API и в логе указывается, какой провайдер реально ответил.

### GigaChat **[ДОПУЩЕНИЕ: сверить с актуальной документацией]**

- Авторизация двухшаговая: по Authorization key (`GIGACHAT_CREDENTIALS`) и scope запрашивается короткоживущий access-токен; его нужно кэшировать в памяти процесса и обновлять до истечения.
- Запросы идут по HTTPS; сертификат российского удостоверяющего центра встроен в код (`app/llm/russian_ca.py`) и добавляется к хранилищу certifi, поэтому от файлов и путей не зависит. Отключать проверку TLS нельзя.
- Токен обновляется под `asyncio.Lock`, чтобы параллельные запросы не запрашивали его одновременно.

### YandexGPT **[ДОПУЩЕНИЕ: сверить с актуальной документацией]**

- Авторизация по API-ключу в заголовке; каталог (`YANDEX_FOLDER_ID`) входит в идентификатор модели.
- Для генерации и эмбеддингов используются отдельные модели.

### Эмбеддинги

- **[РЕШЕНО]** Эмбеддинги берутся у одного провайдера на весь индекс. Смешивать в одном индексе векторы разных моделей нельзя: размерности и пространства разные.
- **[ДОПУЩЕНИЕ]** Провайдер эмбеддингов выбирается один раз в настройках; при его смене индекс пересчитывается полностью. Размерность вектора задаётся в миграции столбца `chunks.embedding` и должна совпадать с выбранной моделью.
- Пакеты текстов отправляются партиями, с повтором при временных ошибках и ограничением параллелизма (`asyncio.Semaphore`).

## 6. Данные

PostgreSQL + pgvector, доступ через SQLAlchemy async и `asyncpg`.

| Таблица | Назначение |
|---|---|
| `users` | Пользователи: email, хэш пароля |
| `api_tokens` | Токены для расширения (хранится хэш, можно отозвать) |
| `repositories` | Подключённый репозиторий: адрес, статус, зашифрованный токен GitHub, последний коммит, id вебхука |
| `index_versions` | Версии индекса: репозиторий, коммит, статус |
| `chunks` | Фрагменты: путь, тип, текст, эмбеддинг, метаданные, версия индекса |
| `jobs` | Очередь задач worker'а |
| `conversations`, `messages` | Диалоги и сообщения |
| `question_logs` | Журнал вопросов (источник `chat`/`mail`, хэш вопроса, статус) |
| `feedback` | Оценки «помогло / не помогло» |

Принципы:
- Все запросы к данным пользователя фильтруются по `user_id`; чужие данные недоступны.
- Векторный индекс (`ivfflat` или `hnsw`) создаётся миграцией.
- Тексты переписки из «Спросить у ИИ» в БД **не сохраняются** **[ДОПУЩЕНИЕ]**; в `question_logs` — только хэш, время и статус.
- Изменения схемы — только через Alembic.

### Очередь задач **[ДОПУЩЕНИЕ]**

Отдельного брокера нет. Worker в цикле забирает задачи из `jobs` запросом `SELECT … FOR UPDATE SKIP LOCKED`, что безопасно при нескольких экземплярах worker'а. Задача хранит тип, параметры, статус, число попыток и ошибку. Обработка идемпотентна: повторный вебхук или повторная задача не портят индекс.

## 7. Индексация

- Содержимое репозитория скачивается через GitHub API (`httpx`, async), без `git clone`.
- В индекс идут исходный код, документация, README, конфигурация; по возможности issues и PR.
- Пропускаются бинарные и слишком большие файлы (`MAX_FILE_BYTES`) и репозитории больше `MAX_REPO_FILES`; пропуски отражаются в статусе.
- **Секреты в индекс не попадают**: файлы вроде `.env`, ключей и сертификатов исключаются заранее.
- Фрагмент хранит путь, тип, коммит, дату, автора.
- После успеха обновления указатель на активную версию индекса переключается одной транзакцией; ответы всегда ссылаются на коммит, по которому они построены.
- Вебхук принимается только с корректной подписью (`GITHUB_WEBHOOK_SECRET`); подпись сравнивается постоянным по времени сравнением.
- Если у токена нет прав на создание вебхука, статус подсказывает настроить его вручную.

## 8. Ответы и поиск

- Поиск: вектор вопроса → ближайшие фрагменты в `chunks` (только активная версия индекса и только репозиторий пользователя).
- Контекст для нейросети собирается только из найденных фрагментов.
- Системный промпт явно разделяет инструкции и данные; команды внутри файлов или писем игнорируются.
- Правило честности: если подтверждения нет, статус `not_found` или `partial`, без выдуманных файлов и фактов.
- Каждый ответ содержит: текст, источники, статус, коммит индекса, провайдера.
- Режим «Спросить у ИИ»: из текста черновика выделяются вопросы, цепочка переписки используется как контекст; письмо ничем не блокируется и не отправляется.
- Ответ можно получать потоком (SSE), пока идёт поиск и генерация.

## 9. API

Подробный контракт будет в автоматически генерируемой схеме OpenAPI (`/docs`, `/openapi.json`). Основные группы:

| Группа | Пути |
|---|---|
| Аккаунт | `POST /auth/register`, `/auth/login`, `/auth/refresh`; `POST/DELETE /auth/api-tokens`; `GET /me` |
| Репозиторий | `POST /repo/connect`, `GET /repo/status`, `DELETE /repo` |
| Вебхук | `POST /github/webhook` |
| Вопросы | `POST /qa/ask`, `GET /qa/conversations/{id}`, `GET /sources/{id}` |
| Почта | `POST /mail/ask` |
| Обратная связь | `POST /feedback` |

**Единый формат ошибок:** `{ "code": "...", "message": "...", "retryable": true|false }`, сообщения на русском. Для необработанных исключений наружу отдаётся только общий код; детали пишутся в лог без содержимого запросов.

**Аутентификация [ДОПУЩЕНИЕ]:** JWT для веб-приложения, отдельный отзываемый API-токен для расширения.

## 10. Запуск и разработка

### Локально

```bash
cp .env.example .env        # заполнить ключи и секреты
docker compose up --build   # api + worker + postgres
```

После старта: `http://localhost:8000/docs` — Swagger.

### Миграции

```bash
docker compose exec api alembic upgrade head
```

### Тесты

```bash
docker compose exec api pytest
```

- Внешние сервисы (GigaChat, YandexGPT, GitHub) в тестах мокируются (`respx`).
- Обязательные проверки: изоляция данных между пользователями; подпись вебхука; идемпотентность индексации; fallback между провайдерами; ответ `not_found`; невозможность выполнить команду, спрятанную в файле или письме.
- Перед завершением задачи запускаются тесты и линтер (`ruff`).

## 11. Безопасность, логирование и открытые вопросы

### Безопасность

- Пароли — только хэш (argon2); токены API хранятся хэшем.
- Токены GitHub — только шифрованными.
- Ключи LLM — только из окружения; в логи и ответы не попадают.
- Проверка прав на каждый запрос: пользователь видит только свой репозиторий, индекс и историю.
- Ограничение частоты запросов на вход и на вопросы **[ДОПУЩЕНИЕ]**.
- Защита от prompt injection (раздел 8).

### Логирование

- Структурированные логи в stdout.
- В логах нет текстов вопросов, переписки, содержимого репозитория, паролей и ключей.
- Записываются: время, маршрут, код ответа, длительность, провайдер LLM, статус ответа.

### Открытые вопросы

1. Нужен ли отдельный брокер задач вместо таблицы `jobs`, если нагрузка вырастет.
2. Точные параметры авторизации и модели GigaChat и YandexGPT — команда пришлёт позже; до этого LLM-слой реализуется только по интерфейсу.
3. Размерность вектора `chunks.embedding` — зависит от модели эмбеддингов, фиксируется в миграции после получения параметров GigaChat.

## 12. Фактическое состояние (20.10.2026)

- **Индексация.** `app/services/indexer.py`: дерево репозитория и blob'ы через GitHub API, фильтр бинарных файлов, lock-файлов и секретов (по имени и по содержимому), нарезка на фрагменты (~1200 символов), issues и PR, эмбеддинги GigaChat. Версия индекса собирается рядом с активной и переключается одной транзакцией; при обновлении неизменённые фрагменты копируются вместе с векторами. Повторная обработка того же коммита ничего не делает.
- **Worker.** `python -m app.worker`, очередь в таблице `jobs` (`FOR UPDATE SKIP LOCKED`), три попытки с экспоненциальной паузой, возврат брошенных задач. Ошибка доступа GitHub даёт статус `reauth_required` (старый индекс отвечает), долгий сбой при существующем индексе оставляет `ready` с `last_error`, без индекса даёт `error`.
- **Ответы.** `app/services/qa.py` + `retrieval.py`: фильтр оффтопа, векторный поиск (pgvector `<=>` в PostgreSQL, косинус в Python на SQLite), порог `QA_MIN_SIMILARITY`, JSON-ответ модели; ответ без подтверждающих фрагментов понижается до `not_found`. Содержимое репозитория и переписки передаётся в тегах как данные, закрывающие теги в нём нейтрализуются.
- **Вебхук.** Создаётся при подключении (токен с правом `admin:repo_hook` и публичный `PUBLIC_BASE_URL`), иначе в статусе подсказка. Репозиторий ищется без учёта регистра, обновляются все пользователи репозитория, учитывается только основная ветка.
- **LLM.** GigaChat основной, YandexGPT запасной: при недоступности, 429 и 5xx запрос уходит на запасного, ошибка авторизации не маскируется. Ответ API содержит провайдера, который ответил.
- **Миграции.** Alembic (`alembic/`), `python -m scripts.migrate` применяет их при старте API; базу, созданную старой версией, приводит к текущей схеме без потери данных.
- **Лимиты.** Скользящее окно в памяти процесса: вход и регистрация по IP, вопросы и почта по пользователю (`RATE_LIMIT_ENABLED`).
- **Журнал запросов.** Только метод, путь без query, код и время; access-лог uvicorn отключён.
- **Тесты.** e2e-сценарии (`tests/test_e2e*.py`) против настоящих локальных IMAP/SMTP и respx-заглушек GitHub, GigaChat и YandexGPT; `E2E_DATABASE_URL` прогоняет их на PostgreSQL.
- **Известные ограничения.** SSE отдаёт ответ одним куском (потоковой генерации нет, потому что ответ — JSON); лимиты не общие между процессами API; идентификаторы источников меняются после переиндексации; почтовый клиент открывает новое IMAP-соединение на каждый запрос.
