# Платформа ответов по документации

Сервис, который отвечает сотрудникам на вопросы **только по документации проекта**: каждое утверждение с
цитатой и ссылкой на источник. Если ответа в документации нет, вопрос уходит администраторам проекта, а их
ответ возвращается к человеку и пополняет базу знаний. Если нужен человек, открывается обращение в поддержку
(с зеркалом в Jira).

Платформа не привязана к каналу: её встраивают через **открытый API** в любую систему — почту, мессенджер,
портал. Интегратор передаёт своих пользователей (их id) и статусы, платформа делает всё остальное.
В репозитории есть демо-интеграция — почтовый клиент.

RAG-ядро перенесено из проекта Innopolis (корпоративный Telegram-бот БАРС Груп) и доработано под
многопроектную платформу: разделы документации с доступом по участнику, изоляция загрузок по проектам.

## Сервисы

| Сервис | Что делает | Документация |
|---|---|---|
| [`services/llm`](services/llm) | Скрытый RAG-сервис: агент с инструментами, гибридный поиск (векторы + BM25 → RRF → реранкер), проверка цитат и чисел кодом, кэши ответов, аналитика, индексация DOCX / PDF / MD / TXT с описанием картинок | [README](services/llm/README.md) |
| [`services/admin`](services/admin) | Ядро платформы: открытый API `/v1`, сайт для владельца, админов и поддержки (вход: логин + пароль + код проекта), вопросы без ответа, обращения и Jira, события для интеграций | [README](services/admin/README.md), [API](docs/API.md) |
| [`services/mail`](services/mail) | Демо-интеграция: почтовый клиент IMAP/SMTP со своими пользователями, «Спросить у ИИ» по черновику, чат, уведомления | [README](services/mail/README.md) |

Схема и решения — [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). Контракт для интеграторов — [docs/API.md](docs/API.md).

```
интеграции (почта, боты, порталы) ──/v1──►  admin  ──внутренняя сеть──►  llm (RAG)
владелец / админы / ТП ──сайт────────────►  admin  ──►  Jira (ТП)
```

## Как это работает для людей

1. Интегратор создаёт проект от имени пользователя (`POST /v1/projects`). Создатель получает **код проекта**
   (показывается один раз) и ссылку, чтобы задать пароль для сайта администратора.
2. Владелец входит на сайт (логин + пароль + код проекта) и загружает документацию по разделам.
3. Интегратор назначает статусы своим пользователям: `admin`, `support` или `user`. Админы и поддержка получают
   ссылку на пароль; пользователям сайт не нужен.
4. Пользователь спрашивает в своём канале → ответ с источниками и картинками из документации.
5. Ответа нет → вопрос у админов на сайте → их ответ приходит пользователю событием и (по желанию) сохраняется в базу.
6. «Позовите человека» → обращение в ТП → переписка на сайте или в Jira → ответы приходят пользователю.

## Быстрый старт (Docker, VPS)

```bash
python3 scripts/setup_env.py            # services/*/.env с согласованными секретами
```
```bash
nano services/llm/.env                  # вписать OPENROUTER_API_KEY
```
```bash
docker compose up -d --build
```

- почта (демо): http://localhost:3000 — регистрация, «Проекты» → создать проект;
- сайт администратора и открытый API: http://localhost:3001 (Swagger — `/docs`).

На сервере с доменами: `python3 scripts/setup_env.py --domain platform.example.com --mail-domain mail.example.com`,
перед `admin-web` и `mail-web` — HTTPS (Caddy / nginx с Let's Encrypt). Порты меняются переменными
`ADMIN_PORT`, `MAIL_PORT`. Наружу публикуются только два nginx; `llm`, базы, Qdrant и Redis портов не открывают.

Новый ключ для своей интеграции:
```bash
docker compose exec admin python -m admin_api.cli integration-create my-bot "Мой бот"
```

## Модели

Все LLM-вызовы RAG идут через OpenRouter (агент DeepSeek, реранкер, описание картинок Gemini Flash, эмбеддинги
`google/gemini-embedding-001`); модели и цепочки запасных задаются в `services/llm/.env`. Без ключа платформа
работает, но на вопросы отвечает «сервис ответов недоступен» и не индексирует документы.

## Проверка

```bash
make test            # тесты трёх сервисов и сквозной тест платформы (без Docker, сети и ключей)
```
```bash
make check-web       # типы, линтеры и сборка двух фронтендов
```

Сквозной тест (`tests/e2e`) поднимает настоящие `llm`, `admin` и `mail` в одном процессе и проходит путь
от создания проекта до ответа поддержки; подменяются только языковая модель и эмбеддинги.
