# «Решено» (fintech_academy)

AI-помощник по проекту и почтовый клиент в одном веб-приложении. Идея: большинство вопросов «коллеге в личку» уже имеют ответ в README, коде, документации, issues и истории коммитов. «Решено» находит этот ответ сам и показывает, откуда он взят.

## Что умеет

### Ассистент по проекту

- Пользователь регистрируется и подключает **один репозиторий GitHub** (публичный или приватный по собственному токену).
- Сервис индексирует репозиторий: исходный код, README и документацию, конфигурацию, а также issues и pull requests.
- На вопрос («Где описан релиз?», «Как настроен деплой?», «Какой формат у этого API?») система ищет по индексу и отвечает **с источниками**: файл, фрагмент, коммит.
- Если подтверждения в проекте нет, ответ честно получает статус `not_found`, без выдуманных файлов и фактов.
- После каждого коммита в основную ветку индекс **обновляется сам** (вебхук GitHub). Пока идёт обновление, ответы строятся по прошлой версии индекса, затем версия переключается атомарно.
- Спросить можно в **чате** или кнопкой **«Спросить у ИИ»** при написании письма: вопросы выделяются из текста черновика, цепочка переписки служит контекстом. Ничего не отправляется автоматически, итоговое действие всегда за пользователем.
- Ответ можно оценить («помогло / не помогло»).

### Почтовый клиент

- Подключение ящиков по **IMAP/SMTP** (Gmail, Яндекс, Mail.ru, iCloud и другие).
- Папки, список и поиск писем, чтение, перенос, удаление, скачивание вложений.
- Отправка писем с вложениями и сохранение черновиков.
- Тексты писем не сохраняются в базе данных, а читаются с почтового сервера. HTML очищается перед показом.

## Как это работает

```
 Браузер ──► frontend (nginx) ──/api──► api (FastAPI) ──► PostgreSQL + pgvector
                                          │                   ▲
                                          │ задачи (jobs)     │ фрагменты, векторы
                                          ▼                   │
                                       worker ───► GitHub API ┘
                                          │
                          api и worker ───┴──► GigaChat (основной) / YandexGPT (запасной)
```

**Индексация.** При подключении репозитория `api` создаёт задачу в таблице `jobs`. `worker` забирает её, скачивает содержимое через GitHub API (без `git clone`), режет файлы на фрагменты (~1200 символов), считает эмбеддинги и записывает в `chunks`. Бинарные файлы, lock-файлы и секреты (`.env`, ключи, сертификаты) в индекс не попадают. После пуша GitHub шлёт вебхук, и пересчитываются только изменённые файлы.

**Ответ на вопрос.** Вопрос превращается в вектор, по pgvector ищутся ближайшие фрагменты активной версии индекса только репозитория этого пользователя. Из них собирается запрос к нейросети. Содержимое репозитория и переписки передаётся как **данные, а не инструкции**: команды, спрятанные в файле или письме, игнорируются. Ответ без подтверждающих фрагментов понижается до `not_found`.

**LLM.** GigaChat основной, YandexGPT запасной. При таймауте, 429 и 5xx запрос один раз уходит запасному. Ошибка авторизации не маскируется. В ответе API указано, какой провайдер реально ответил. Эмбеддинги берутся у одного провайдера на весь индекс: `gigachat` (по умолчанию) или `cloudru`.

## Быстрый старт

Нужны Docker и Python 3.12 (только для скрипта настройки).

```bash
python back-end/scripts/setup_env.py --fetch-ca
docker compose up --build
```

Первая команда создаёт `back-end/.env`, сама генерирует `SECRET_KEY`, `ENCRYPTION_KEY` и `GITHUB_WEBHOOK_SECRET` и скачивает сертификат российского УЦ для GigaChat в `back-end/certs/`. Если `.env` уже есть, существующие значения не меняются.

Дальше остаётся вставить ключи в `back-end/.env` (см. таблицу ниже).

После запуска:

- сайт: http://localhost:3000
- API и Swagger: http://localhost:8000/docs

Без ключей всё поднимается, но чат отвечает «LLM не настроен», а индексация ждёт ключей. Почта от ключей не зависит.

Токен GitHub в настройки сервера не вносится: каждый пользователь вводит его сам при подключении приватного репозитория (нужны права на чтение и `admin:repo_hook`, чтобы сервис мог сам создать вебхук). Пароль ящика пользователь вводит при подключении почты: для Gmail, Яндекса, Mail.ru и iCloud нужен **пароль приложения**, а не основной пароль.

## Переменные окружения

Локально они читаются из `back-end/.env`, на платформе задаются в панели. Образец: `back-end/.env.example`.

| Переменная | Обязательно | Назначение |
|---|---|---|
| `DATABASE_URL` | да | Строка подключения `postgresql+asyncpg://…`. В compose по умолчанию указывает на сервис `postgres` |
| `SECRET_KEY` | да | Ключ подписи JWT. На проде свой, не менее 32 символов |
| `ENCRYPTION_KEY` | да | Ключ Fernet для токенов GitHub и паролей ящиков |
| `GIGACHAT_CREDENTIALS` (или `GIGACHAT_AUTH_KEY`) | для LLM | Authorization key из [кабинета GigaChat](https://developers.sber.ru/studio) |
| `GIGACHAT_CA_BUNDLE` | нет | Доп. сертификат УЦ. Сертификат российского УЦ уже встроен в код (`app/llm/russian_ca.py`), так что переменная не обязательна |
| `GIGACHAT_SCOPE`, `GIGACHAT_MODEL`, `GIGACHAT_EMBEDDINGS_MODEL` | нет | Область доступа и модели GigaChat |
| `EMBEDDINGS_PROVIDER` | нет | `gigachat` (по умолчанию) или `cloudru` |
| `API_KEY` (или `CLOUDRU_API_KEY`) | для `cloudru` | Ключ Cloud.ru для эмбеддингов |
| `YANDEX_API_KEY`, `YANDEX_FOLDER_ID`, `YANDEX_MODEL` | нет | Запасная нейросеть YandexGPT: включается сама, если GigaChat недоступен |
| `LLM_PRIMARY`, `LLM_FALLBACK` | нет | Основной и запасной провайдер чата |
| `QA_MODE` | нет | `strict` (по умолчанию): ответ только с подтверждением из файлов; `chat`: разговорный режим |
| `PUBLIC_BASE_URL` | для автообновления | Публичный адрес сервиса. GitHub шлёт вебхуки на `PUBLIC_BASE_URL/github/webhook`; на локальном адресе вебхук не создаётся, индекс обновляется переподключением репозитория |
| `GITHUB_WEBHOOK_SECRET` | рекомендуется | Секрет подписи вебхука GitHub |
| `LOG_LEVEL`, `LLM_TIMEOUT_SEC`, `MAX_REPO_FILES`, `MAX_FILE_BYTES` | нет | Логирование, таймаут модели, лимиты индексации |

Приложение падает при старте, если нет обязательных переменных, а не при первом запросе.

Сгенерировать ключи:

```bash
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

Первая команда даёт `ENCRYPTION_KEY`, вторая подходит для `SECRET_KEY` и `GITHUB_WEBHOOK_SECRET`. Если поменять `ENCRYPTION_KEY`, сохранённые токены и пароли ящиков перестанут расшифровываться.

## Что внутри docker compose

| Сервис | Назначение |
|---|---|
| `frontend` | nginx со сборкой фронтенда; `/api` проксируется на `api`. Первый сервис в файле: платформа отдаёт на домен именно его |
| `api` | FastAPI; при старте сам применяет миграции (`python -m scripts.migrate`) |
| `worker` | Индексация репозиториев и обновление по коммитам |
| `postgres` | PostgreSQL 16 с расширением pgvector |

Файл `back-end/docker-compose.yml` остался от автономного запуска только бэкенда и для сайта не нужен.

## Деплой на App Platform (Timeweb)

Платформа читает только `docker-compose.yml`: в нём нет `volumes`, `env_file` и портов 80/443, а сайт (`frontend`) идёт первым сервисом. Локальные добавки (том БД, `back-end/.env`, порт API) вынесены в `docker-compose.override.yml`, платформа его не использует. Сертификат для GigaChat копируется в образ `api` на этапе сборки.

Контейнеры получают только те переменные, которые перечислены в блоке `environment` файла `docker-compose.yml`. Новую переменную нужно добавить и туда, и в панель.

Все секреты задаются переменными окружения приложения в панели: `SECRET_KEY`, `ENCRYPTION_KEY`, `GIGACHAT_CREDENTIALS`, `GITHUB_WEBHOOK_SECRET`, `PUBLIC_BASE_URL` (адрес сайта) и при необходимости `YANDEX_*`. Без `DATABASE_URL` используется Postgres из compose **без тома**: данные теряются при пересоздании контейнера. Для продакшена укажите управляемую БД с расширением pgvector.

## API

Полный контракт: Swagger на `/docs` и схема на `/openapi.json`. Основные группы:

| Группа | Пути |
|---|---|
| Аккаунт | `POST /auth/register`, `/auth/login`, `/auth/refresh`; `POST/DELETE /auth/api-tokens`; `GET /me` |
| Репозиторий | `POST /repo/connect`, `GET /repo/status`, `DELETE /repo` |
| Вебхук | `POST /github/webhook` |
| Вопросы | `POST /qa/ask`, `GET /qa/conversations/{id}`, `GET /sources/{id}` |
| «Спросить у ИИ» | `POST /mail/ask` |
| Почта | `/mail/accounts` (подключение, папки, письма, поиск, вложения, перенос, удаление, отправка, черновики) |
| Обратная связь | `POST /feedback` |

Ошибки имеют единый формат `{ "code": "...", "message": "...", "retryable": true|false }`, сообщения на русском. Для браузерного расширения выдаются отдельные отзываемые API-токены.

## Разработка и проверка

Бэкенд:

```bash
cd back-end
pip install -e ".[dev]"
pytest                      # e2e-сценарии на локальных заглушках GitHub, GigaChat, IMAP и SMTP
ruff check .
E2E_DATABASE_URL=postgresql+asyncpg://... pytest tests/test_e2e_knowledge.py   # то же на настоящем PostgreSQL
```

Живая проверка ключей: `python -m scripts.check_llm` (в Docker: `docker compose exec api python -m scripts.check_llm`).

Фронтенд:

```bash
cd frontend
npm ci
npm run dev        # сервер разработки Vite
npm run check      # typecheck, ESLint, Stylelint, Steiger, Prettier
npm run build
```

Изменения схемы БД делаются только через Alembic. Тесты проверяют, в том числе, изоляцию данных между пользователями, подпись вебхука, идемпотентность индексации, fallback между провайдерами, ответ `not_found` и невозможность выполнить команду, спрятанную в файле или письме.

## Безопасность

- В `back-end/.env.example` раньше лежал настоящий `GIGACHAT_AUTH_KEY`. Он остался в истории git: **отзовите его в кабинете GigaChat** и выпустите новый.
- Для продакшена задайте свои `SECRET_KEY`, `ENCRYPTION_KEY` (иначе у `docker compose` подставляются публичные dev-значения) и `GITHUB_WEBHOOK_SECRET`.
- Пароли пользователей хранятся только хэшем (argon2), токены API тоже.
- Токены GitHub и пароли ящиков хранятся только зашифрованными (Fernet). Тексты писем в БД не сохраняются, в журналы не попадают ни тексты вопросов и писем, ни query-строки.
- Все запросы к данным фильтруются по пользователю, чужие данные недоступны.
- Вебхук принимается только с верной подписью, сравнение постоянное по времени.
- Почтовый клиент защищён от SSRF: подключения к приватным и локальным адресам запрещены (`MAIL_ALLOW_PRIVATE_HOSTS=false`).
- Есть ограничение частоты запросов: вход и регистрация по IP, вопросы и почта по пользователю.

## Известные ограничения

- SSE отдаёт ответ одним куском: потоковой генерации нет, потому что ответ модели имеет формат JSON.
- Лимиты запросов хранятся в памяти процесса и не общие между процессами API.
- Идентификаторы источников меняются после переиндексации.
- Почтовый клиент открывает новое IMAP-соединение на каждый запрос.
- В MVP один репозиторий на пользователя, без команд и организаций GitHub.
