# Платформа ответов по документации

Сервис отвечает сотрудникам на вопросы **только по документации проекта**: каждое утверждение — с цитатой и
ссылкой на источник. Нет ответа в документации — вопрос уходит админам проекта, их ответ возвращается человеку и
пополняет базу знаний. Нужен живой человек — открывается обращение в поддержку (с зеркалом в Jira).

Платформа не привязана к каналу: её встраивают через **открытый API** (`/v1`) в почту, мессенджер, портал.
Интегратор передаёт своих пользователей (их id), платформа хранит проекты, статусы, ответы и обращения.
В репозитории есть демо-интеграция — почтовый клиент с кнопками «Спросить у ИИ» и «Ответить с ИИ».

RAG-ядро перенесено из проекта Innopolis (корпоративный Telegram-бот) и доработано под многопроектную платформу:
разделы документации с доступом по участнику, изоляция загрузок и поиска по проектам.

## Как это работает

### Сайт администратора — владелец, админы, поддержка

1. **Регистрация** на сайте: логин и пароль (требований к паролю нет).
2. После входа — экран **«Проекты»**:
   - **«Создать проект»** — вы владелец; **код проекта** показывается один раз (потом — в «Настройках»);
   - **«Войти как админ»** — по коду, который дал владелец (понизенный владельцем админ код не вернёт);
   - список своих проектов: у одного аккаунта их может быть несколько, переключение — в меню аккаунта.
3. В проекте: документация по разделам, участники и их разделы, вопросы без ответа, частые вопросы, статистика,
   обращения в поддержку, настройки (код проекта, Jira — только владелец).

| Статус | Что может на сайте |
|---|---|
| владелец | всё, включая код проекта, Jira, назначение админов и поддержки |
| админ | документация, пользователи, вопросы без ответа, статистика, частые вопросы, обращения |
| поддержка | только обращения |
| пользователь | на сайт не ходит — задаёт вопросы в своём канале (почте и т. п.) |

### Интеграция — где задают вопросы

- Пользователи интеграции — её собственные id (`external_id`). Статусы им ставит владелец или админ
  (`PUT /v1/projects/{id}/members/{external_id}`); правила, кто кого может назначить, проверяет платформа.
- Проект можно создать и из интеграции (`POST /v1/projects`); а в проект, созданный на сайте, пользователь
  интеграции входит админом по коду (`POST /v1/projects/join`).
- Кому выдан статус админа или поддержки, получает ссылку `…/setup?token=…`: открывает, входит или
  регистрируется на сайте — проект добавляется к его аккаунту.
- Ответы, которые приходят позже (админ ответил, поддержка написала, документация обновилась), — события:
  опрос `/v1/events` или вебхук с подписью.

Полный контракт — [docs/API.md](docs/API.md).

### Почта (демо-интеграция)

- Свои пользователи (email + пароль), ящики по IMAP/SMTP.
- «Проекты»: создать проект, войти админом по коду, выбрать текущий, выдать коллегам статусы по email.
- **«Спросить у ИИ»** в черновике: вопросы из письма ищутся в документации — возможно, письмо отправлять не нужно.
- **«Ответить с ИИ»** у входящего письма: черновик ответа по документации над цитатой; чего в документации нет,
  помечено «[уточнить: …]». Письмо отправляет сам человек кнопкой «Отправить».
- Чат с ИИ, «Связаться с поддержкой», уведомления об ответах админов и поддержки.

## Сервисы

```
интеграции (почта, боты, порталы) ──/v1──►  admin  ──внутренняя сеть──►  llm (RAG)
владелец / админы / поддержка ──сайт─────►  admin  ──►  Jira
```

| Контейнер | Что это | Наружу |
|---|---|---|
| `admin-web` | nginx: сайт администратора + прокси `/panel/api`, `/v1`, `/jira` | порт `3001` |
| `admin` | ядро платформы (FastAPI): аккаунты сайта, проекты и статусы, вопросы → RAG, вопросы без ответа, обращения и Jira, события для интеграций | — |
| `admin-db`, `admin-redis` | Postgres ядра; Redis для лимитов | — |
| `llm` | скрытый RAG-сервис: агент с инструментами, гибридный поиск (векторы + BM25 → RRF → реранкер), проверка цитат и чисел, кэши, индексация DOCX / PDF / MD / TXT с описанием картинок | — |
| `llm-db`, `qdrant`, `llm-redis` | Postgres RAG (ходы, оценки, задачи), векторная база, Redis (сессии диалогов, кэш) | — |
| `mail-web` | nginx: сайт почты + прокси её API | порт `3000` |
| `mail-api`, `mail-db` | демо-почта (FastAPI) и её Postgres; к платформе ходит только через `/v1` | — |
| `caddy` | только в продакшене: HTTPS для двух сайтов | `80`, `443` |

**Три сервиса — три независимых `docker-compose.yml`** (`services/<сервис>/docker-compose.yml`), корневой файл
их только подключает. У каждого свои базы и Redis; при старте сервисы не ждут друг друга: без `llm` работает
`admin` (кроме ответов ИИ), без `admin` — почта (кроме ИИ и проектов). Связь — через общие сети:
`platform_rag` (admin ↔ llm), `platform_api` (интеграции → admin), `platform_web` (Caddy → сайты). Почта не видит
`llm` и чужие базы; `llm` недоступен ни из интернета, ни из почты. Схема и решения —
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Где что лежит

```
services/
  admin/                  ядро платформы                            docker-compose.yml — запуск отдельно
    backend/admin_api/    api/ — HTTP (v1, panel, public), services/ — логика (accounts, projects, asking, questions,
                          escalations, jira, events…; rag — клиент к llm), db/ — модели и сессии, core/ — настройки,
                          безопасность, ошибки; миграции — backend/alembic
    frontend/             сайт администратора (React, FSD: pages / widgets / features / entities / shared) + nginx
  llm/                    RAG-сервис                                 docker-compose.yml — запуск отдельно
    rag_service/          api/ — HTTP, core/ — настройки и БД, agent/, retrieval/, index/, ingest/, faq/, cache/,
                          analytics/, sources/ (git, confluence); prompts/, config/ — промпт и справочник продукта
  mail/                   демо-интеграция                            docker-compose.yml — запуск отдельно
    backend/mail_api/     api/ — HTTP, services/ (mailbox — IMAP/SMTP, platform — клиент /v1), db/, schemas/, core/
    frontend/             почтовый клиент (React, FSD) + nginx
docs/                     API.md — контракт для интеграторов, ARCHITECTURE.md — схема и решения
tests/e2e/                сквозной тест трёх сервисов в одном процессе
scripts/setup_env.py      генерация services/*/.env с согласованными секретами
deploy/                   Caddyfile и .env.example для продакшена
docker-compose.yml        подключает три сервиса; docker-compose.prod.yml — надстройка с HTTPS (Caddy)
```

У каждого сервиса свой README: [admin](services/admin/README.md), [llm](services/llm/README.md),
[mail](services/mail/README.md).

## Запуск (Docker)

Секреты — один раз (файлы `.env` в git не попадают):

```bash
python scripts/setup_env.py
```

**Всё целиком.** Впишите `OPENROUTER_API_KEY` в `services/llm/.env` и выполните:

```bash
docker compose up -d --build
```

**Без ИИ** — быстро, без сборки `llm` (регистрация, проекты, участники, почта работают; вопросы к ИИ и загрузка
документации отвечают «сервис недоступен»): назовите только сайты, compose поднимет их сервисы с базами.

```bash
docker compose up -d --build admin-web mail-web
```

**Один сервис** — из его папки, например только почта:

```bash
docker compose -f services/mail/docker-compose.yml up -d --build
```

- сайт администратора и открытый API: http://localhost:3001 (Swagger — `/docs`);
- почта: http://localhost:3000.

Миграции баз `admin` и `mail` применяются при старте их контейнеров. Ключ для своей интеграции:

```bash
docker compose exec admin python -m admin_api.cli integration-create my-bot "Мой бот"
```

## Модели

Все вызовы моделей в RAG идут через OpenRouter (агент DeepSeek, реранкер, описание картинок Gemini Flash,
эмбеддинги `google/gemini-embedding-001`); модели и запасные цепочки — в `services/llm/.env`. Без ключа платформа
работает, но на вопросы отвечает «сервис ответов недоступен» и не индексирует документы.

## Проверка

```bash
make test        # тесты трёх сервисов и сквозной тест (без Docker, сети и ключей)
make check-web   # типы, линтеры и сборка двух фронтендов
```

`Makefile` рассчитан на Linux/macOS (`.venv/bin`); на Windows — `.venv\Scripts\python -m pytest` в папке сервиса.
Сквозной тест (`tests/e2e`) поднимает настоящие `llm`, `admin` и `mail` в одном процессе и проходит путь от
регистрации и создания проекта до ответа поддержки и «Ответить с ИИ»; подменяются только модель и эмбеддинги.

## Деплой

Каждый push в `main` выкатывается на сервер ([.github/workflows/deploy.yml](.github/workflows/deploy.yml)):
GitHub Actions по SSH делает `git reset --hard origin/main` в `~/app` и `docker compose up -d --build`.
На сервере в корне лежит `.env` из [deploy/.env.example](deploy/.env.example) — он подключает
`docker-compose.prod.yml` (Caddy с HTTPS, домены `ADMIN_DOMAIN` и `MAIL_DOMAIN`); `services/*/.env` создаются
`python scripts/setup_env.py --domain <домен сайта> --mail-domain <домен почты>` и в git не попадают.
